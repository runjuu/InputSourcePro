# Additional cursor support

An opt-in experimental feature for displaying Input Source Pro’s indicator using the active application’s input-method caret geometry. Position → Advanced → Additional cursor support provides setup, activation, and removal. It requires Enhanced Mode. The helper and setup utility are embedded in Debug and Release builds; the feature is off by default.

The helper is an auxiliary InputMethodKit palette. It queries the active client's selection geometry and publishes screen coordinates, process ID, session ID, and monotonic timestamp through local distributed notifications. It does not request document text, log keystrokes, insert text, or consume keyboard events. When enabled, the app uses a fresh palette sample first in every app. Accessibility is the fallback when no usable sample is available, except while the helper reports pending confirmation; existing indicator preferences and app exclusions still apply. Samples expire after 750 ms and are cleared when the foreground app changes. Invalid geometry is hidden.

The bundle sets `ComponentInvisibleInSystemUI` to hide the palette from macOS's input menu. This Boolean is defined by `kComponentBundleInvisibleInSystemUIKey` in the SDK's `TextServices.h`; Apple also uses it for background palette input methods. Setup and removal remain in the app. Upgrading an existing visible helper refreshes the input-menu agent to clear the cached row. The earlier `TISVisible` setting did not hide the menu entry in a live test. The updated helper builds and remains registered, enabled, and selected. The user confirmed the menu entry disappeared and reported cursor tracking still working; their screenshot shows the input menu without the helper row.

The helper polls adaptively in common run-loop modes: every 1/60 second during input or caret movement, then every 250 ms after 350 ms without activity. The main app relays timing and foreground process ID for keyboard, click, drag, and scroll events through its existing event monitors, at most once per 16 ms; it does not send key contents. Ordinary pointer movement does not accelerate polling. Input-method key callbacks also queue a refresh after returning the event to the client. Activity immediately interrupts the idle wait. Programmatic caret movement discovered by an idle check starts a fast burst too. Nearby caret movement is published immediately. A jump exceeding half a line vertically or two line heights horizontally is confirmed on a later fast poll before publication; continuously changing large moves wait at most 50 ms plus the next poll. This suppresses brief incorrect geometry without delaying ordinary character-by-character movement in most apps. Codex uses confirmation for every changed position, including the initial sample: its brief incorrect coordinates can be less than one character away when text is short. This adds a fast-poll confirmation delay in Codex instead of relying on jump distance. Unchanged samples remain immediate. Codex no longer has a forced timeout that accepts changing geometry: matching samples must be separated by a fast-poll interval with no new input between them. The 50 ms unconfirmed-movement limit applies only to other apps. While confirmation is pending, the app retains a still-fresh confirmed position, then hides it after the existing 750 ms expiry instead of querying Accessibility. Pending messages do not refresh old geometry; their own freshness expires if the helper stops. Unchanged geometry is published only every 250 ms to keep the sample fresh. These intervals are not an end-to-end latency guarantee: client processing, cross-process queries, and rendering can add delay. Without the main app activity relay, input not delivered to the palette may wait for the next idle check.

Focus changes are tracked through Accessibility notifications when useful roles are available. Known non-input roles suppress both helper coordinates and Accessibility fallback; window/group roles remain unknown so custom editors such as Zed still work. Entering a different field clears the old sample and waits for that field’s geometry. Each recognized input focus gets a new identifier echoed by the helper, so late positions or deactivations from an earlier field are ignored. This adds event-driven focus checks, not per-frame Accessibility polling. The existing rule hiding the dot under an overlapping default indicator remains unchanged.

## Build and run

The Xcode build embeds signed helper tools in `Contents/Helpers/CaretPalette`. The build script follows the app’s architectures, deployment target, and signing identity. Distribution signing/notarization still needs release validation.

For standalone diagnostics, run from the repository root:

```sh
bash Tools/CaretPalette/build.sh
/tmp/isp-zed-palette-build/setup install '/tmp/isp-zed-palette-build/ISP Palette Control.app'
/tmp/isp-zed-palette-build/setup authorize
/tmp/isp-zed-palette-build/setup status
```

The installer validates bundle identity and signature, stages the new helper, stops the old helper, preserves a backup outside the Input Methods directory, replaces the bundle, and registers it. It restores the previous selected state after updating. Backups live under `~/Library/Application Support/InputSourcePro/CaretPaletteBackups/`. The diagnostic bundle identifier remains `dev.inputsourcepro.inputmethod.PaletteControl`, preserving existing consent.

`authorize` opens macOS's native Allow dialog if the palette is not already enabled. It waits up to 30 seconds and only reports enabled state after reading the system flag. It does not press Allow. Verify persistence with `status` in a fresh process. Palette sources are absent from the normal Add Input Source list.

If Settings opens without a permission dialog, explicitly retry with:

```sh
/tmp/isp-zed-palette-build/setup authorize --reopen-settings
```

That option gracefully closes Settings first, then sends the request to a fresh instance. It stops if Settings refuses to close. `authorize --check-request` validates the private descriptor round trip without opening Settings or changing permission. Unsupported private symbols and timeouts are reported as failures.

Use **Set up… → Install and continue** in Position settings. The sheet installs the helper, requests native permission, and checks selection before reporting success. Closing a pending permission request prevents late approval from activating tracking. Once setup succeeds, tracking is used automatically. **Uninstall…** removes the helper after confirmation; there is no separate toggle or Manage sheet. The indicator uses existing appearance and visibility settings.

Installation is the source of truth. An installed, authorized helper starts automatically when Enhanced Mode is available, including on relaunch. The former `isAdditionalCursorSupportEnabled` preference and prototype environment flag are no longer read. A missing helper stays uninstalled; missing permission requires explicit setup and startup never opens a consent dialog.

`setup start` and `setup stop` select/deselect the palette for diagnostics without changing the keyboard source or revoking consent. Starting the helper alone does not start Input Source Pro's indicator.

Quit the app to deselect the helper; permission and installation remain. It resumes automatically on the next launch while Enhanced Mode is available. Turning off Enhanced Mode also stops tracking. `setup uninstall` deselects and disables the source, stops its process, and removes the installed bundle and validated installer backups. It refuses unrelated bundles and symlinks. After successful removal, it terminates the current session’s TextInputMenuAgent so macOS rebuilds the input menu without a cached palette row. This briefly closes an open input menu; it does not restart the main app or change the selected keyboard source. Failure to refresh the menu is reported as a warning because the helper has already been removed. macOS may retain cached registration or consent after file removal. Deleting the main app alone does not remove this separately installed helper.

Setup uses a background utility process so waiting for permission or file operations does not block the settings UI. Each status check runs in a fresh process. Activation and resume selection also use the setup utility: an already-running app can retain a TIS cache from before installation or authorization. The app starts receiving coordinates only after a fresh process confirms selection. Regression coverage checks activation ordering, automatic use of installed helpers, and keeping removed helpers uninstalled. Installation keeps a backup and restores it if registration fails.

## Evidence and limits (2026-10-03)

- Settings integration: 184 tests passed, including denied permission, failed selection, late approval after closing setup, failed uninstall, removal boundaries, and registration rollback. The live settings row, management sheet, and uninstall confirmation were inspected; removal was cancelled to preserve the working installation. Relaunching without the prototype environment flag restored the enabled/selected helper. Fresh-machine native consent and reinstall after removal remain unverified. A later live uninstall exposed and fixed a nil TIS lookup crash and two legacy research installations left behind by the original uninstaller; all three helper identities are now covered. The fixed uninstall removed the legacy bundles and backup, and the refreshed system input-source list showed only the user’s normal input sources. All 188 tests passed, including the actual missing-source lookup and legacy removal boundaries.
- Debug and Release builds succeed. Embedded cursor-helper and setup signatures verify. A whole-app deep signature check flags `Contents/Library/LoginItems/LaunchAtLoginHelper.app`; distribution signing remains unverified.

- A native Settings consent request successfully enabled the diagnostic palette on the test machine.
- The user manually typed Pinyin in stock Zed, both with the palette off and with it selected. Candidates and Chinese text insertion worked in both cases. The diagnostic helper also recorded changed caret coordinates during that test.
- Some synthetic typing trials produced literal `nihao` despite the Pinyin selected flag. Those trials are not evidence that physical keyboard composition is broken.
- The Swift helper's coordinates reach the Debug app, which displays its actual always-on indicator in Zed. Suspending the helper hides the indicator after the freshness timeout; resuming restores it. Switching to another app clears Zed's position.
- Unit tests cover invalid rectangles, stale/future timestamps, mismatched process IDs, old focus samples, and AppKit coordinates on a display left of the main display.
- The user confirmed the integrated indicator follows movement and Pinyin works, but reported growing horizontal drift. The helper incorrectly supplied a document offset to an API expecting an inline-session-relative offset. Using zero for the auxiliary palette fixed the drift: clicks at five Chinese-character boundaries produced caret x coordinates 91.365, 106.365, 121.365, 136.365, and 151.365.
- The user confirmed movement between rows and scrolling. A horizontal window move shifted the reported caret by the same 110 points. Switching between two Zed scratch windows and returning changed/restored their respective coordinates. Programmatic resizing returned success but the window retained its dimensions, so resize behavior is not counted as verified.
- After reducing polling to 1/60 second, a 60-second Zed scratch-document check received 232 notifications and four distinct caret rectangles. The shortest publication interval was 16.0 ms; the median was 266.0 ms, reflecting idle heartbeat coalescing. Notification delivery took a median 1.33 ms and maximum 2.92 ms. This measures helper-to-observer delivery, not physical-key-to-indicator latency.
- Adaptive polling replaces that continuous 60 Hz polling. Tests cover returning to idle, sustained activity, and waking after a long idle; the full suite passed 150 tests. The installed app relayed live input activity and the helper published changed positions. During quiet five-second measurement windows with zero activity signals and zero caret changes, the helper used approximately 0.4–0.6% of one CPU core and sent 18–19 position heartbeats. A separate 20-second sample containing unclassified activity used 2.9%; it is not an idle benchmark. Physical-key-to-visible-indicator latency and energy impact have not been measured.
- Repeated installation preserved enabled/selected state; a fresh setup process confirmed both flags. Damaged signatures and unrelated bundles were rejected without replacing the installed executable. The Swift permission descriptor passed its private-API round trip.
- Sleep, display-sleep, and session-inactive notifications now clear the cached position and block incoming samples until all suspension reasons end. Resume selects the palette only if it remains enabled but has become deselected, without changing the keyboard or restoring revoked consent. Tests cover overlapping and repeated lifecycle events; actual hardware sleep/wake remains untested.
- This machine's existing permission persisted after a public disable request, so the new setup tool's first-time consent path could not be re-tested with this identity. The native request mechanism was proven earlier, but a clean installation/permission test is still required. Physical multi-display, resizing, login/restart, and actual sleep/wake remain unverified.
- Helper updates are bundled with app updates. The coordinate channel still has no authenticated IPC or crash supervisor; these and clean-machine distribution validation remain release-hardening work. Keep the feature experimental.

- A user reproduction in Codex with U.S. English exposed temporary IMK geometry, not marked-text composition: selection offset 22 returned `(605, 92)` and then `(747, 152)` about 19 ms later. Several offsets showed the same temporary location. A geometry filter now confirms large discontinuities before publication. Replaying the captured typing segment accepted 20 correct positions and rejected 17 transient jumps. Regression tests cover that trace pattern, immediate nearby movement/backspace, real row/Home navigation, bounded continuous movement, and invalid geometry; 155 tests passed. The filtered helper is installed, but the user has not yet confirmed the visual result.

## Consent research

Apple's [QA1810](https://developer.apple.com/library/archive/qa/qa1810/_index.html) explains why palette input methods are absent from Keyboard settings' source list and need their own enable/disable UI.

On this test system, the public `TISEnableInputSource` opened Settings but did not enable the palette. Calling private `TISEnableInputSourceWithOptions(source, 2)` from the diagnostic process changed local state but did not persist consent. Calling it directly is not the solution.

The working experiment used `_CreateFlattenedInputSource` to obtain the real input-source descriptor, then sent System Settings an XML property list with `tabID = com.apple.IntlKeyboard`, `inputSourceToBeEnabled = <descriptor>`, and `localizedSenderName`. A Launch Services parameter list contained a `pref` descriptor naming `com.apple.Keyboard-Settings.extension` and a `ptru` descriptor containing that plist. Settings showed its native Allow dialog and persisted permission after user-authorized approval. An already-open Settings instance sometimes ignored this request; relaunching Settings made the experiment work. This is an undocumented, OS-dependent path requiring more investigation before an installer is built.

## Other applications

The helper is no longer restricted to Zed and no longer requires `selectedRange` support before querying current-selection geometry. Some clients implement the geometry query but not document-relative selection ranges. Every received sample must still match the foreground process, be fresh, and contain valid screen geometry. Enabling the helper does not guarantee support in every editor: clients that return neither input-method nor Accessibility geometry still cannot provide a caret position.

- Follow-up: the user reported that large-jump filtering helped long text but short text still jumped. Code inspection showed sub-threshold changes and initial samples bypassed confirmation. Codex now confirms all changed samples; five new tests cover nearby transients, initial positioning, real backward navigation, bounded continuous movement, and returning to the accepted position. All 160 tests passed. The user reported improvement but occasional backward jumps remained.

- Further confirmation changes remove Codex’s forced 50 ms acceptance and restart confirmation after new input. A pending-state message prevents both new and in-flight Accessibility queries from supplying fallback positions while the helper is validating geometry. Regression tests cover timeout bypass, matching positions across input events, retained confirmed positions, pending expiry/focus changes, and fallback suppression. All 166 tests passed. These close identified code paths; elimination of the remaining intermittent visual jump is not yet confirmed.

- Focus follow-up: the user reported entry flashing and movement near the mouse after blur. Code inspection found only foreground-app tracking, no field-focus validation, and gaps in fallback suppression when helper sessions cleared. Added focus role gating, field identity reset, acquisition confirmation, and a focus identifier in the helper protocol. All 170 tests passed, including custom-editor compatibility. The manual traces did not capture a complete focus/blur reproduction, so the visual outcome remains unverified. The default indicator’s intentional overlap hiding can independently make the dot disappear and return.
